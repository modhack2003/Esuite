### QA-01 — retained finding evidence

`Finding` now carries `evidence: List<Exchange>` beside `evidenceIds`. The retained copy is a bounded durable SNAPSHOT, not a pin on the live capture: pinning would have had to exempt specific exchanges from history rollover, `clearHistory()`, save-time exchange halving and project deletion, so every one of those four paths would need to know about findings. A snapshot instead lives in the durable region that no prune path touches and is immutable, so the disposal paths stay exactly as they were. `evidenceIds` remains the authoritative reference list, so `EvidenceRetention.missing(finding)` is exactly the set difference and a reference with no snapshot is an explicit state in the UI rather than a dangling id. `EvidenceRetention.snapshot` caps both bodies at `Limits.EVIDENCE_BYTES` (16 KiB) on a UTF-8 code-point boundary, keeps base64 values 4-character aligned, and keeps the existing `StoredBody.truncated` label when it cuts a response.

`WorkspaceSchema.CURRENT_VERSION` is 3. The new `2 -> 3` step BACKFILLS deployed 1.0.x vaults: every `evidenceId` that still resolves to a live exchange is snapshotted, so existing findings are repaired rather than merely defaulted to empty; ids whose exchange is already gone keep reporting the missing state. The step reuses the live `Exchange`/`Finding` serializers, which is only valid while those shapes are unchanged relative to v2 — a later shape change must pin a frozen DTO. Fail-closed behaviour is unchanged: missing/non-integer/newer versions and a missing step still throw "Unsupported workspace version" and `load()` writes nothing.

The backfill is BOUNDED by the same durable budget `addFinding` admits under, because a load runs no admission check: `WorkspaceBudget.durableHeadroom(workspace)` reports what the document has left of the 16 MiB durable region, `EvidenceRetention.backfill(findings, exchanges, budget, cost)` admits snapshots in reference order while that headroom lasts, and a reference it cannot afford keeps its explicit missing state. Without that bound an upgraded vault could load fine (a load writes nothing, so no data is lost) and then fail EVERY encrypted save with `CapacityExceeded`, because `WorkspacePersistence.prepare` can only halve `exchanges` and never touches the durable region — and the writer's effective budget is `byteBudgetForHeap` = `min(VAULT_BYTES, maxHeap / 12)`, which is lower still on a low-heap device. `WorkspaceMigrationTest` pins a v2 upgrade sized to leave less headroom than one snapshot costs: the finding survives field-for-field, its reference stays missing, and the migrated workspace still satisfies `requireDurableCapacity`.

`addFinding` admits the finding WITH its snapshot, so the durable budget decides before the observation is accepted and an accepted observation can never lose its evidence later; at capacity it is rejected with an evidence-aware message (`WorkspaceBudget`'s own string is unchanged). `removeEvidence(findingId, exchangeId)` drops a snapshot but keeps the id. `ReportExporter.sanitized` runs retained snapshots through the same redaction/path/header omission as capture history, so the new durable field cannot leak bodies, paths or header values. Findings now show one row per reference: a `finding_evidence_N` control reveals the snapshot (status, duration, identity, source, completeness, headers, body with its truncation label) with a review-before-sending handoff to API Lab, a reference with no snapshot states that evidence was not retained, and both deletion paths confirm first.

### QA-02 — pending drafts kept in memory

QA-02: pending editor text now lives in `core/EditorDrafts.kt`, a ViewModel-owned holder (`AppViewModel.drafts`) keyed by `DraftKey(projectId, editor, identity)` over the 16-value `Editor` enum, so a draft survives module switches, rotation and Activity recreation. Screens are pure readers/writers — a missing key means "unset", so the screen's own fallback applies — which is what the increment-2 layout rework reuses. `identity` is set only for an editor that declares `Editor.identityScoped`, and every key is built through `DraftKey.of(projectId, editor, identity)` so that declaration is the one place the rule lives rather than a decision repeated at each call site (see the identity rule below). Memory is bounded per editor by `Editor.valueChars` and overall by `Editor.entries.size * 20` = 320 entries, dropping the least recently written beyond that. `valueChars` is 64 Ki by default but `Limits.REQUEST_BYTES` (256 KiB) for the two editors whose text is parser INPUT rather than a field value — `ToolsInput`, which feeds `importOpenApi`/`importHar`/`importCurl`, and `ApiRaw`, which feeds `DraftParser.raw` — because the uniform smaller cap cut a legitimate import-sized paste on entry and then surfaced it as a JSON/parser syntax error with no indication the text had been truncated. In practice only one project's drafts are retained at a time, because `selectProject` clears the outgoing project's.

Resolved decision: IN-MEMORY ONLY. `rememberSaveable`/`SavedStateHandle` were rejected because the platform writes saved instance state to disk outside the encrypted vault, which would leave cookies, tokens and auth headers in plaintext. Nothing in the draft path touches `AppState.workspace`, so typing triggers no encrypted save (the persistence collector observes `state.map { it.workspace }`) and no platform saved-state write. The explicit consequence is that drafts are LOST ON PROCESS DEATH, and the UI says so: `ui/DraftNotice.kt` renders that sentence once in API Lab, once in Findings and once in Tools (which hosts Workflows). An explicit opt-in "Keep this draft" vault write is DEFERRED — it is the same durable-write surface as QA-09/11's selected redacted evidence reports and optional encrypted local backup/restore, so it should be designed with them rather than bolted on here.

Moved off screen-local `remember`: API Lab headers/raw-import/saved-name/identity-headers, Findings title/detail (still cleared on a successful save), Tools input, Workflows P1–P4/sequence-names/token-pointer, and Browser address/edit/script (`BrowserScreen` sits inside `MainActivity`'s `when(screen)`, so it is destroyed on every switch). Four text fields deliberately stay screen-local and are NOT drafts, because the agreed `Editor` set has no key for any of them: the Tools output field, which is derived from the input plus the pressed transformation; the Traffic filter, which is a view control over a list rather than authored content; and Home's `project_name`/`project_origin`, which are entered BEFORE a project exists, so there is no project to key a draft by and keying them to the currently selected project would both strand entries under the previous project and change what the fields show after a successful create. Giving pre-project fields their own retention is open scope, not done here. `mode`/`preview` in Workflows and `panel`/`output`/`console`/`reveal` in Browser likewise stay local transient view state.

Writer rules in `AppViewModel`: wholesale draft replacement (`draft(RequestDraft)` — therefore also `importCurl`, the raw-HTTP import and loading a saved request — plus `replay(Exchange)`) refreshes the `ApiHeaders` editor from the new draft's headers, but ONLY when those headers actually differ from the current draft's. A replay/import visibly refreshes the editor, while method/URL/body keystrokes, which also go through `draft()`, can never overwrite half-typed header text. `selectProject` clears the OUTGOING project's drafts (it already discards that project's request draft, so retaining half of it would be incoherent) and `deleteProject` clears the deleted project's. `identity(value)` runs `CredentialPolicy.stripHeaderLines` over the retained `ApiHeaders` draft, so a retained request-header draft is stripped exactly as the ViewModel draft already is; that new line-level filter reuses the existing `names` regex, tests only the text before the first colon, and never throws on malformed or blank lines (unlike `DraftParser.headers`, which does).

The identity rule, declared by `Editor.identityScoped` and applied by `DraftKey.of`: an editor whose text is handed to ONE identity's own credential surface is keyed by identity as well as project, so an A→B switch leaves A's pending text under A's own key and the field always shows the SELECTED identity's pending text or, when that key is unset, its own fallback. Three editors qualify. `ApiIdentityHeaders` falls back to the identity's saved `IdentityConfig`, and `configureIdentity` clears the key on success — the way a saved finding clears its title/detail drafts — so the editor falls back to what was just stored. `BrowserEdit` backs `browser_cookie_input`, whose text `browser_set_cookie` writes into the selected identity's ISOLATED COOKIE JAR. `BrowserScript` is evaluated in the selected identity's own profile-bound WebView, which is the lifetime it had before drafts existed. `BrowserAddress` is deliberately project-wide: a URL is not credential-bearing and page loads stay explicit through Go.

Keying these by project alone was wrong in two ways the review caught in successive passes. For `ApiIdentityHeaders` the field showed A's stripped leftovers, B's saved headers became invisible, and `api_save_identity` wrote A's leftovers into B's `IdentityConfig`. For `BrowserEdit` the regression was introduced by this branch — it replaced `remember(project.id, identity)`, which discarded the text on every identity change — and it meant a Set-Cookie value typed under A stayed in the field after switching to B, so pressing Set stored identity A's cookie in identity B's isolated jar. That is the same cross-identity carryover in a path where cookie-jar separation is the product contract, which is why the declaration now lives on the enum instead of at each call site. Identity-scoped editors are deliberately NOT in the `identity()` strip list: with the identity dimension in the key there is nothing to carry across, and stripping configured header names out of the editor that authors them would delete exactly the text the user is editing. `EditorDraftsTest.identityHeaderDraftsCannotCrossBetweenIdentities` and `browserCookieAndScriptDraftsCannotCrossBetweenIdentities` pin both separations on the JVM, the second also pinning the identity-scoped set itself so a newly added editor cannot silently default to project-wide.

Nothing is claimed about it; it stays OPEN SCOPE. Autocorrection itself is addressed, because `autoCorrectEnabled = false` omits `TYPE_TEXT_FLAG_AUTO_CORRECT` from the field's input type.

### QA-05 — in-flight result attribution

QA-05: a response that started under one identity could previously be displayed under another. `send()` captured a snapshot at launch but then assigned `selected = response` unconditionally, so an A→B switch while a request was in flight left A's response shown under a header reading B; `identity()` only nulled `selected` at switch time, which did not help a result landing afterwards. `runPayloads()` and `runMacro()` applied `selected`/`taskProgress` the same way, and nothing in the UI stated which identity a displayed response came from.

The fix separates RECORDING from APPLICATION. `core/ResultAttribution.kt` adds `RequestContext(generation, projectId, identity)`, `accepts(started, current)` (true only when generation, project and identity all still match) and `label(exchange, projectName)` (renders the exchange's OWN identity, source, project and UTC timestamp — never the currently selected identity). `AppViewModel` holds a `contextGeneration` counter bumped by `identity()` (only on an actual change), `selectProject()`, `deleteProject()`, `loadWorkspace()` and `eraseVault()`; each of `send()`, `runPayloads()` and `runMacro()` captures `started` at launch. `record()` stays UNCONDITIONAL in every path (including the comparison A/B legs and the error exchange), so no evidence is ever dropped and the exchange is always in Traffic. Only the `selected`/`comparison`/`message`/`taskProgress` and the macro's extracted-token application are gated on `accepts(started, current)`. When the context no longer matches, an honest message is shown — "A result for identity A arrived after you switched to B. It is recorded in Traffic and was not applied here." — with no cookie-leakage claim (none was established). The existing 429/503 stop, one-second spacing, no-retry, cancellation and finally-block semantics are unchanged; cancellation still records nothing and reports "Request cancelled".

The displayed response now states its origin: `ResultAttribution.label(...)` is prepended to the API Lab response panel title and to the Traffic "Exchange detail" panel body, both resolving the project name from the exchange's own `projectId`. All existing test tags are unchanged.

A sequence that is superseded mid-run keeps its own wording. `runMacro` gates the token extraction on `accepts()`, so a later step containing `{{token}}` would otherwise hit `require(token != null)` and have the generic `catch` report "Sequence stopped: {{token}} is unavailable before the first extraction" — an extraction-order message for a user who simply switched identity. That branch now checks the context first and reports the superseded message instead; a genuinely out-of-order `{{token}}` still throws the identical message it always did.

The delayed-response instrumented case WAS added, not blocked: `com.squareup.okhttp3:mockwebserver:4.12.0` resolved offline as `androidTestImplementation`, confirmed by `:app:compileDebugAndroidTestKotlin`. Three new `DeviceBoundaryTest` cases drive the real `AppViewModel` on the main looper against a MockWebServer-backed endpoint, pre-seeding the vault with a loopback HTTP origin so `send()` runs end to end without TLS. TWO policies have to allow that, and the first record of this named only one. `ScopePolicy` permits `http` at the engine because the HTTPS-only gate lives in `createProject` and not on a loaded project (exactly as the JVM `ApiEngineTest` relies on) — but the request is also governed by the platform network security policy, which the shipped config sets to `cleartextTrafficPermitted="false"` with no exception, so OkHttp would reject the request before opening a socket and the cases could not pass on any device. The fix is scoped to the debug variant: `app/src/debug/res/xml/network_security_config.xml` keeps the HTTPS-only base config and adds a loopback-only `domain-config` for `127.0.0.1`/`localhost`, which `app/src/androidTest` picks up because `testBuildType = "debug"`. The shipped release config and `android:usesCleartextTraffic="false"` are untouched (that manifest attribute is ignored on API 24+ whenever a network security config is present, and `minSdk` is 28, so the config file is the authority in both variants). These cases therefore cannot run against a release build by design. The cases themselves: a delayed 200 and a delayed error each switch identity mid-flight and assert the exchange IS recorded under identity A but is NOT applied to `selected` under B, plus a cancel variant asserting nothing is recorded and the cancellation message stands.

QA-05's acceptance also says "including tasks", and the three cases above drive `send()` only, so a fourth case covers a RUNNER gate: `parameterTaskSupersededMidRunStillRecordsEveryLegAndReportsTheSwitch` starts a two-leg `runPayloads()` plan against delayed MockWebServer responses, switches identity while the first leg is in flight, and asserts that BOTH legs are recorded in Traffic under identity A with source "Parameter runner", that the superseded message replaces "Parameter task complete", and that `taskProgress` never advanced past the switch. `runPayloads` is the runner driven because it needs no saved requests; `runMacro`'s identical `accepts()` gate and its superseded-`{{token}}` branch are still covered only by `ResultAttributionTest` in isolation plus the JVM-level wording, so the macro runner's cross-context behaviour remains UNPROVEN on a device. Like every other case in this file, the new one compiles here and has not been executed.

### QA-08 — deferred browser profile cleanup

QA-08: deleting a project after normal Browser use failed outright. `BrowserProfiles.clearProject` wrapped `store.deleteProfile(name)` in `check(...)`, and `AppViewModel.deleteProject()` aborted the WHOLE deletion on that throw, which is what the Vivo audit reproduced twice ("Cannot delete in-use profile ..._A", then success only after a cold restart). The provider is behaving correctly: [ProfileStore.deleteProfile](https://developer.android.com/reference/androidx/webkit/ProfileStore#deleteProfile(java.lang.String)) also rejects a profile that is loaded in memory through the profile access APIs, and `BrowserScreen` loads one via `WebViewCompat.setProfile` on every visit. Destroying every WebView does not undo that and there is no API to unload a profile, so cleanup can only be DEFERRED — it cannot be made synchronous.

Deferred-cleanup lifecycle: `BrowserProfiles` now reports instead of throwing. `CleanupResult(deleted, pending, unsupported)` splits what the provider accepted from what it refused; both a `false` return and a thrown `IllegalStateException` count as `pending`, because providers differ on which they use. `clearProject(projectId)` attempts both identities, `sweepOrphans(liveProjectIds)` attempts every ESuite profile whose project is gone, and `clearAllEsuiteOwned()` attempts all of them. `deleteProject()` no longer aborts: the workspace deletion completes exactly as before and the refused profile is recorded in `AppState.pendingProfileCleanup`, with a message naming the profile, stating that WebView still has it loaded, that cleanup is retried automatically when ESuite restarts, and that `retryProfileCleanup()` can be used now. `loadWorkspace()` runs the sweep on the main thread right after a successful load (the `viewModelScope.launch` body is back on Main once the `withContext(storageDispatcher)` load returns) and sets the pending list from its result, so the cold restart the audit observed is now the automatic resolution path rather than a manual workaround.

Derived, not persisted — the design decision and its reason: the pending-cleanup record is `ProfileNames.orphans(store.allProfileNames, liveProjectIds)`, computed from the provider's own list measured against the live project ids. There is therefore NO new persisted field, NO new `WorkspaceSchema` version (`CURRENT_VERSION` stays at 3, the value QA-01 set) and no migration to get wrong, the record cannot be lost or desynchronised from the provider, and it is readable when the vault is NOT — which is exactly what the recovery gap needed. `core/ProfileNames.kt` is a pure Android-free seam (`name`, `parse`, `orphans`) so that ownership rule is decidable on the JVM: `ProfileNamesTest` pins it over seeded-random project ids plus the adversarial literals `esuite__A`, `esuite_x_C`, `Esuite_x_A`, `default`, `Default` and `other_app_A`, asserting an orphan is never a live project's profile, the default profile, a foreign profile or a malformed name, and that `name`/`parse` round-trip. Deletion is prefix-scoped twice over: a candidate must parse as an ESuite name, must not be `Profile.DEFAULT_PROFILE_NAME`, and must actually be reported by the store.

Recovery gap closed. The not-ready/unreadable-vault screen in `MainActivity` gains a confirmed "Remove all ESuite browser profiles" action that calls `clearAllEsuiteOwned()` and reports deleted/pending counts on that same screen; it needs no vault, because the `esuite_` prefix identifies what this app created without the project index. `eraseVault()` now attempts the same cleanup AFTER the vault erase succeeds — ordered that way so a failed erase leaves ESuite's profiles in place instead of deleting them and reporting it late on the next successful load — and carries its report into the next successful load message. `EraseVaultDialog`'s text was wrong and is corrected — it told the user WebView data was separate and that projects had to be deleted individually first; it now states that ESuite's own profiles go with the erase by name prefix and that other apps' WebView data and the default profile are untouched. Pending cleanup and the retry control are rendered beside the delete control in `WorkspaceControls` (new tags `workspace_profile_cleanup`, `retry_profile_cleanup`), because the audit found the deletion outcome was otherwise discoverable only by scrolling back to the top status line. No existing test tag was renamed or dropped.

FORENSIC ON-DISK ERASURE IS NOT CLAIMED anywhere in this increment. `deleted` means the provider ACCEPTED the deletion; it may schedule the file removal asynchronously. Every user-facing string says the profile was handed to Android WebView for deletion, or that a pending profile's data is still on the device until it is removed — none of them says the data is gone.

## Current runtime limits and semantics

- API requests are limited to 256 KiB bodies and 64 KiB total headers; response capture is capped at 256 KiB and explicitly labelled when truncated or Base64 encoded.
- Exact scheme/host/port scope. Android UI projects require HTTPS; API redirects and automatic retries are disabled.
- Identity switches, replay and comparison strip observed/known/configured authentication headers. Body credentials remain unchanged and require review. Explicit manual cookies override the selected jar.
- API cookie jars are memory-only. The browser’s explicit To API jar action replaces the current identity jar with cookies matching the selected URL; metadata-supported transfers preserve domain/path/Secure/HttpOnly. This supports real A/B comparison after signing into each isolated browser profile. Without cookie metadata support, fallback transfer uses host/root-path defaults and says so. Configured auth headers, saved requests and evidence are encrypted. WebView cookies/cache are separate platform-managed app-private profile data, outside the workspace cipher.
- History is capped at 100 exchanges. Durable collections/config/notes have a 16 MiB admission budget; the whole encrypted vault is capped at 32 MiB, with a smaller save budget on low-heap devices (max heap / 12). History may be pruned to fit. Saved collections and observations are rejected at capacity rather than silently dropped.
- Workspace write failures preserve the previous AtomicFile. Unknown/missing keys and corrupt files do not trigger plaintext fallback or automatic replacement. Native backup recovery is part of the latest emulator test.
- Sanitized exports omit bodies, paths, query values, headers, identity config and finding free text. The origin/generated IDs remain. Export requires preview and a known on-device provider. Rich raw evidence export is not implemented.
- Inspector snapshots are capped at 16,000 selected-HTML characters and 24,000 displayed evaluation characters; selection metadata and a display prefix explicitly identify truncation.
- Browser history is **URL/method/request-header metadata only**. No browser response/body capture is claimed. Unsupported profile features disable this browser rather than sharing test identities silently.
- Browser navigation is scoped; third-party subresources can load normally but are not recorded. No native JavaScript bridge is exposed. TLS errors are cancelled.
- Parameter runs: up to 50 sequential requests, at least one second apart, stop on 429/503 or transport failure. UI exposes four payload lists with matching substitution positions. No automatic retry/resume.
- Sequences: up to 10 saved requests; optional first-response JSON Pointer extraction into `{{token}}`; stop on non-2xx. URL tokens are encoded, header/body substitutions are literal.
- cURL import is a conservative parser, not shell execution. OpenAPI supports JSON 3.x; HAR import supports textual request drafts and filters exact origin.
- AWS review analyzes supplied JSON structurally; it does not contact an account or fully evaluate conditions, SCPs or effective privileges. JWT claims remain unverified; token statistics do not prove cryptographic randomness.
